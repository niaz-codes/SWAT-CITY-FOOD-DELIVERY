# Changelog

## [Unreleased]

- **Checkout stops loading forever: the device cart is now synced to the server before the bill quote.** The checkout screen computes its bill with `GET /orders/quote`, which reads the SERVER cart, but the app only pushed the local (AsyncStorage) cart to the server inside `placeOrder` — so on a fresh server cart the quote answered 400 "Your cart is empty" and the screen sat on "Preparing your bill…" forever. New `cartApi.sync` in `src/services/api.ts` (single implementation, reused by `placeOrder`, safe to call repeatedly since `POST /cart` replaces the whole basket) and Checkout now runs sync → quote in one sequence, also adopting the quote's embedded `methods` list as a fallback for payment availability. Customer-facing demo checkout copy is neutralised (method reads "Quick Pay", button "Place order", plain "Confirm your order" dialog, no demo wording) per the owner's decision; the "DEMO — NOT REAL MONEY" marking stays on every server-side record, the create-order `demoMode` label and the admin Payments badge (documented in `PAYMENTS.md`). Verified live against Railway: empty-server-cart quote fails as before, then sync → quote returns a positive total with the methods list carrying the demo label (8/8 checks); offline `test-demo-payments.ts` passes in both flag states.

- **Demo checkout + payments land end to end, always labelled "DEMO — NOT REAL MONEY".** A fourth registered payment provider (`backend/src/services/payments/demo.ts`) reuses the exact Easypaisa/JazzCash `initiateOnlinePayment` → `verifyOnlinePayment` machinery: checkout keeps sending the order through the real pipeline, and only the payment itself is simulated — the backend is its own verifier, no gateway and no wallet credential is ever contacted. The mode is wired off by default and exists only when the backend env sets `DEMO_PAYMENTS_ENABLED="true"` (zod-validated, `demoPaymentsEnabled` in `src/config/env.ts`); nothing a client sends can enable it. `demo` became a distinct payment method (DB check constraints `orders_paymentmethod_check`/`payments_method_check` migrated via the schema migrations block, refs use a `DM` prefix, the payment sweeper now sweeps it too), so demo rows stay filterable apart from production transactions. Every settled demo payment credits the ADMIN wallet as a `commission` ledger row named `demo_<transactionRef>` — checked manually and backstopped by the new unique partial index `wallet_transactions_demo_ref_key` so a re-verify can never double-credit. The customer app shows a "Demo Pay" method (amber, availability driven by `GET /payments/methods`), asks for an explicit "Demo checkout — NOT REAL MONEY" confirmation, skips the browser handoff, toasts "Demo payment recorded — NOT REAL MONEY", and the pre-order note states the order goes through the real pipeline while the payment is simulated. The admin panel's Payments page shows an amber "Demo — not real money" badge plus the linked order number. Real Easypaisa/JazzCash code paths are untouched (ref prefixes `EP`/`JC` unchanged; verified by `npx tsx src/scripts/test-demo-payments.ts` in both flag states, 23 assertions). Live flow: `npx tsx src/scripts/e2e-demo-checkout.ts` mints a QA-customer token and drives checkout → verified `paid` → idempotent re-verify → 409 on duplicate payment → same-order replay on duplicate idempotency key → exactly one admin ledger row. Storage gained a reusable `uploadBuffer` (dedup refactor) plus `backend/src/scripts/seed-demo-images.ts`, a keyword-matched harvester that re-hosts images into the project's own Supabase Storage `demo-images/` folder for future menu items created without a photo — the live DB already has photos everywhere, so it recorded a no-op. The customer app now actually renders `imageUrl` where it existed all along: `ArtTile` draws the photo over its gradient with automatic emoji-tile fallback on load errors, and FoodCard, RestaurantCard, Cart, Favorites, the Restaurant hero and the FoodDetails disc all show real photos now.

- **The launcher icon keeps the original logo on solid white — no transparency.** `logo.png` has a transparent canvas and it rendered oddly under Android's launcher masks (and on older launchers), so the icon now uses `assets/icon-white.png` (the logo flattened onto an opaque white 1024×1024 square) as the general `icon`, and `assets/adaptive-icon-white.png` (the logo scaled to 80% centered on the same white canvas) as the Android adaptive-icon foreground with `backgroundColor` flipped from `#0E3F3A` to `#FFFFFF`; the padded dark-green variant remains only as the adaptive `monochromeImage` source for themed icons. `android.versionCode` bumps 1 → 2 (synced to `build.gradle`) so the new APK installs as a clean update and the launcher refreshes the icon.

- **The app launcher icon now uses the brand logo.** `app.json` points `icon` (and, on Android 8+, the adaptive-icon foreground and monochrome layers) at `assets/logo.png`; the adaptive foreground is a new `assets/adaptive-icon-logo.png` — the logo scaled to 780px and centered on a transparent 1024×1024 canvas so Android's circular/squircle launcher mask does not crop the artwork against the existing `#0E3F3A` background. `npm run prebuild` regenerated every `android/app/src/main/res/mipmap-*` launcher density, and the next EAS APK build ships the new icon.

- **WhatsApp ordering channel added to the customer app.** New reusable pieces: `src/utils/whatsapp.ts` (pure number/message helpers + the two configured order lines 03450050667 (primary) and 03453232555 (secondary), Pakistani numbers normalised to `92`-digits-only `wa.me` format), `src/components/WhatsAppButton.tsx` (solid/ghost/compact CTA reusing the single `assets/whatsapp.png` brand icon) and `src/components/WhatsAppContactDialog.tsx` (primary/secondary chooser that opens the `https://wa.me/<number>?text=<summary>` deep link — universal on Android, iOS and web). Buttons wired on the food details screen (compact icon beside the quantity stepper), restaurant page (chat-to-order under the hero), cart (ghost "Order via WhatsApp" under Checkout with the full basket: per-item lines, subtotal, delivery fee, total) and order tracking/confirmation (compact icon beside Cancel / Back-to-home with order lines, total, placed time and current status). WhatsApp is an alternative channel only: it never creates or pays for an app order and never flips a order status. Covered by `npx tsx scripts/test-whatsapp-links.ts` (24 assertions, found and fixed a `0092`-prefix normalisation bug before shipping); documented in `docs/WHATSAPP_ORDERING.md`.

- **Restaurant portal gains reports + new-order alerts, and the app finally cancels and rates for real.** The backend answers owner-scoped `GET /restaurant/reports?range=today|7d|30d|quarter` (delivered revenue, per-day order/revenue series, top dishes with quantity, popular dish ids, kitchen pipeline and cancel/reject counts); admin-web gets a `/portal/reports` page (KPIs, revenue-and-orders chart, top-dish ranking) reachable from a new sidebar tab, and the Orders page now alerts on arrival: a two-note chime (mappable to mute), a toast, an optional desktop notification (permission asked on opt-in) and a "New" pill on fresh rows — all driven by the existing 20 s poll with module-level last-seen state so re-entering the page never replays old orders. On mobile, the tracking screen's Cancel button now calls `POST /orders/{id}/cancel` with a required reason gathered from tap-friendly presets or free text (it previously faked a success toast without any API call — the order stayed live), the button hides once the backend window (pending → ready) closes, and delivered orders can be rated: 1-5 stars + optional note posting a purchase-verified restaurant review (`POST /reviews` with `orderId`, 409 handled as "already rated"). `src/services/api.ts` gains `orderApi.cancelOrder` and `reviewApi`.

- **The admin panel is also live on Railway.** A new `admin-web` service was created in the same `swat-city-backend` project and Railpack builds it as a vite static site (`npm install` → `tsc -b && vite build`, served by Caddy with SPA routing) at `https://admin-web-production-e2fa.up.railway.app`. The `VITE_API_BASE_URL` build variable was verified inlined into the shipped bundle, and the backend `CORS_ORIGIN` now allowlists this origin. Deployment gotcha learned and documented: a plain `railway up` from a subfolder archives the whole repository (the first admin deploy built the mobile root `package.json` and booted Metro); scoped deploys must run `railway up ./admin-web --path-as-root --service admin-web`. `DEPLOYMENT.md` gains an "Admin panel on Railway" section and the backend runbook documents the same flag as a determinism tip; `admin-web/railway.json` is legacy Nixpacks config kept for reference since Railpack's auto-detection is what actually builds the panel. The existing Vercel panel keeps working; its `VITE_API_BASE_URL` should still be flipped to the Railway API URL in the Vercel dashboard.

- **Restaurant owners get a real web portal, and the panel becomes role-aware.** The backend `restaurant` role now has a full portal in the same admin-web app: owners sign in with the same two-step email code and land on `/portal/*` (orders, menu, profile — `layouts/PortalLayout.tsx`, `pages/portal/Portal orders|Menu|Profile`) built only on the owner-scoped `/restaurant/*` endpoints. The portal can confirm → prepare → ready orders (with reject/cancel + reason while still cancellable), search the kitchen queue and refresh it every 20 s, manage dishes (create/edit/delete, category tabs, prices, prep time, calories, availability switch, per-dish photo upload) and edit the profile (description, contact, location, delivery fee/min-order/free delivery, opening hours, banner photo) plus an open/busy/closed kitchen switch in the header. Admins keep their console: the panel's login accepts both roles, routes each to its own home (`/portal/orders` vs `/dashboard`), bounces wrong roles home instead of to a login they already passed, and the Restaurants admin page gained an "Awaiting approval" filter, an approve/hide action, a "Visible to customers" switch in the edit form and an owner-email field to link an existing owner account to a kitchen. Admin-web also dropped the stray backend-only dependencies (`helmet`, `express-rate-limit`). Admin E2E with a real emailed OTP is still pending SMTP access.

- **Mobile is customer+rider only, and the ride/orders flows are real.** Admin screens were removed from the APK (restaurant owners use the web portal; restaurant-role users just see an info screen and sign out). The customer ride flow books, searches and tracks with the real `rideApi` plus socket events (no fake turn lists — navigation hands off to Google/Apple Maps), riders get a dedicated food-delivery job screen (`/rider/jobs`), the rider tracking screen runs the real accept→arriving→started→completed state machine with the customer's real phone number for calls, and the cart now shows the restaurant's own fees (delivery fee, free delivery, minimum order) instead of hardcoded numbers, sending promo codes to checkout where the server prices them.

- **Backend: the owner lifecycle is complete.** Restaurant owners self-register (`POST /auth/register/restaurant` → account + unapproved restaurant in one record), admins approve per kitchen (`PATCH /admin/restaurants/:id` with `isApproved`, or via `approval=pending` list filter), and `ownerEmail` links an existing `restaurant`-role account to a kitchen (unknown emails answer 404 with a clear message). Portal endpoints accept no restaurant id: everything resolves through `ownedRestaurant(req.user._id)`, so cross-restaurant access is structurally impossible. `rideDetail` now populates the customer's name/phone so riders can call. Backend checks: `npm run typecheck && npm test` → 37/37 pass. **Production deploy (`railway up`) still pending** — the new endpoints and fixes live only on localhost until then.

- **Live rider registration no longer fails with `new row violates row-level security policy`.** The production backend can read and write Postgres with the server-only `sb_secret_...` key, but the deployed Supabase Storage client was sending that key in a way Storage treated as anon, so the mandatory camera photo was rejected before any rider row was created. `backend/src/services/storage.service.ts` now uploads and deletes through the Storage REST API with explicit `apikey`/`Authorization` headers, so the path no longer depends on the installed storage-client version. Verified against the live database and bucket on 22 Oct 2026 with the real endpoint (pending rider + Supabase-hosted photo), duplicate registration (`409`), missing photo (`422`), invalid CNIC (`422`) and invalid plate (`422`). **The backend still needs `cd backend && railway up` - the live endpoint keeps returning `403` until this deploy ships.**

- **Rider signup now reuses the rider-profile plate validation.** `riderRegisterSchema` only checked the plate's length, so a value such as `!!` was accepted. It now uses the same `vehiclePlateSchema` as the profile/vehicle endpoints: 1-4 letters, an optional space or hyphen, then 1-4 digits, normalised to uppercase. The regression test now covers the invalid shape and lowercase normalisation.

- **The web admin panel is now a full operations console, not a read-only report.** Every sidebar screen reads live data and writes to the same admin API the mobile app uses: orders (status moves, cancel, rider assignment), rides (cancel with a reason), restaurants (create/edit/delete, cover photo, open/closed), menu (dishes, inline availability, photos, categories), riders (approve/reject with a reason, suspend/activate, approved photo, bike number, vehicle-change review, documents), customers (suspend/activate), payments, wallets and their transactions, withdrawals (approve → process → pay with a reference, reject with a refund), promotions, broadcasts, support tickets with an admin reply, reports and runtime settings (edit in place, add a key).

- **Admin UI rebuilt on a small design system.** A shared kit (`components/ui/`) and semantic CSS-variable tokens replace the old ad-hoc indigo/rose/gray styling with the teal brand, so light and dark mode are driven by one token set. The panel adds a collapsible desktop sidebar, a mobile drawer, a command palette (Ctrl/Cmd+K), a topbar search, pending-work badges, sortable responsive tables that become cards on a phone, skeletons, empty and error states, focus-managed dialogs and drawers, and confirms for destructive actions. The theme choice is light/dark/system, stored as `admin-theme`, applied before first paint by an inline script and synced with the OS when set to system. Charts are theme-aware and use real API series only.

- **Admin support replies were silently dropped.** `supportStatusSchema` did not declare `reply`, and the route replaces `req.body` with the validated payload, so the controller never saw the text. The schema now accepts a 1–1000 character reply. **The backend has not been redeployed**, so this one feature still needs `cd backend && railway up` before production persists replies.

- The login and code screens are rebuilt. **Login** is now a card on the brand gradient with labelled fields, a show/hide password, a live hint of the password policy, an inline error banner instead of a toast that vanishes before it is read, and a clear "we email a 6-digit code" note so the next step is never a surprise. **The code screen** splits the code into six boxes that size themselves to the screen (they fit a 320 dp phone and a tablet alike), advance on their own as digits arrive, accept a pasted code, fall back to the numeric keyboard, shake and explain themselves when the code is wrong, and offer a resend that counts down for 60 s - the window Supabase Auth actually allows - and then works, against the real endpoint. Nothing is faked: the code is always the one the server sent, and a refused send is reported instead of pretending a mail is on its way.

- The app could hang forever on a slow connection. `src/services/client.ts` built an `AbortController` for every request but never handed its signal to `fetch`, so the 12 s and 60 s deadlines never fired and a stalled request left the button spinning with no way out. The signal is now attached, a timeout says so ("the request timed out - check your connection") instead of pretending the network is down, and a connection that failed before anything moved is retried once. An upload is never repeated: the photo may already be partway upstream. The authentication calls also get their own, longer budget (30 s): the backend waits for the mail provider to accept the code and regularly needs 7-9 s, so the old 12 s aborted healthy sign-ins while the mail still arrived - the user was told the login failed and then found a code in their inbox.

- Rider registration no longer fails quietly. The photo was sent as `photo.jpg` / `image/jpeg` no matter what the camera produced, and Android's own editor hands back a PNG - the server then stored PNG bytes under a `.jpg` name. The type and the extension now follow the real file. A photo above the 5 MB limit is caught before it is sent (and the server's own "too large" answer is turned into a sentence the rider can act on) instead of failing after the whole picture travelled over the mobile network. Errors are shown **in the form**, not only in a toast, a second tap can no longer start a second registration, the button says what it is doing while the photo uploads, and a live checklist says which of the nine requirements is still open.

- Uploads no longer depend on a Cloudinary account. The photo upload was switched to Cloudinary, but production has no Cloudinary credentials - the next deploy would have failed **every** upload with "Must supply cloud_name", which takes rider registration down with it, because the camera photo is sent before the account exists. Cloudinary is now optional: with all three credentials the images go there, without them they go to the project's own Supabase Storage bucket. The returned `{ url, publicId }` shape is identical either way, so no caller changes.

- The backend has a test suite and a working linter. `cd backend && npm test` runs 28 checks with the Node test runner: which store an upload goes to, the mime types the app sends, the rider registration payload the Android app produces (accepted as sent, and refused with a reason when the CNIC, phone, password, plate, vehicle or location is wrong), the code verification payload, and the guard that turns a refused email send into a retryable 502. The lint command itself was broken - TypeScript 7 and ESLint 10 had been installed while the plugins still expect their older APIs, so `npm run lint` died before reading a single file; ESLint is pinned back to the supported line, the one library that reads the removed TypeScript API is overridden, and the one rule that reported "parse errors" for every import in the project is off.

- The rider approval path is now checked from end to end. A rider who registers is stored **pending** (`isApproved` false, `pendingApproval` true), the application shows up in the admin list, an admin decision flips both the account and the rider profile, and the rows the check created are removed afterwards. The same script also covers the sign-in paths around it - registration, a duplicate registration, a missing photo, a photo above the size limit, a wrong password, a wrong code, an expired code and a resend - against any backend, live or local.

- **The backend fixes are ready but not live yet.** The error middleware that keeps the real status code and the real message, the optional Cloudinary upload, and the provider's own waiting time in the answer are on the branch, but the Railway account currently refuses deployments ("Deploys have been paused temporarily"). Until it ships, a refused verification mail still answers `500 Internal server error` on the live API instead of the sentence that says how long to wait. `cd backend && railway up --service backend` publishes them.

- The admin web panel now shows **live data on every screen**. Nine of the ten sidebar pages were placeholders that read nothing; they now read the same admin endpoints the mobile app uses (`/admin/orders`, `/admin/restaurants`, `/admin/riders`, `/admin/users?role=customer`, `/admin/payments`, `/admin/promotions`, `/admin/notifications`, `/admin/reports`, `/admin/settings`) and draw the rows, with a search box, the filters the API supports and paging. The rows are a table on a wide screen and one card per row on a phone, so the panel stays usable from a handset. One shared component (`ResourcePage`) does the fetching, searching, filtering and paging for all of them. Writing - approving a rider, moving an order on, sending a broadcast - is still only in the mobile app; the web screens read and report for now.


- The admin web panel now **always** gets to the code screen, and the reason is never a dead end. The step that emails the 6-digit code was failing in silence: the mail provider refuses a second code for the same address while its own cooldown runs, the backend turned that refusal into a blanket `500 Internal server error`, and the panel showed it in a toast that a phone user never saw - so the panel looked like it had no OTP option at all. The panel now keeps the half-finished login in storage (a reload no longer throws the admin back to the password form), shows every failure **in the page** ("the code could not be sent - try again in a moment", "too many codes - wait a couple of minutes"), and retries the send by itself when the provider is cooling down. A wrong or expired code no longer signs the admin out: the `401` handler used to redirect to `/login` and drop the code screen mid-login. The API timeout is 45 s, because sending a code takes 5-8 s.

- Backend: an operational error now keeps its own status code. A refused email send answers **502** with the real message ("we could not send the verification email - please try again in 27 seconds") instead of `500 Internal server error`, so the client can tell the user what to do; unexpected failures still answer a generic 500. A code that was emailed less than a minute ago is now re-used instead of mailing another one, so a second tap on "Sign in" no longer trips the provider's cooldown. **Not deployed yet** - the Railway account has deploys paused.

- The brand is now the full name everywhere: **Swat City Food Delivery**. The splash screen, the login greeting, the app headers, the ride and profile screens, the legal documents, the permission prompts, the admin panel and every transactional email and notification (welcome mail, password notices, order and top-up descriptions, the Supabase Auth mail templates) use the full name instead of "Swat City". Two places keep the short name on purpose, because there it means the city and not the company: the address search field ("Search Swat City") and the delivery charge note ("outside Swat City limits").

- The admin web panel works again on its deployed URL. Three faults were stacked: the production build shipped **no environment variables**, and the module that reads them threw at import, so React never mounted and the page stayed white; the panel signed in through Supabase Auth and then sent that token to the API, which only accepts tokens it signed itself, so every call came back `401`; and the role check read the `users` table directly with the publishable key, which RLS (zero policies, by design) blocks, so login always ended in "Access denied. Admin only.". The panel now signs in through the **backend**, exactly like the mobile app: email + password, then the emailed 6-digit code. The session token it stores is the API's own, and the role comes from the API, so the panel no longer talks to Supabase at all and the zero-policy model in `backend/supabase/schema.sql` still holds. The dashboard also read fields the API never returns (`totalOrders`, `totalRevenue`) and would have shown zeros for every card; it now reads the `totals`/`today`/`charts` shape the mobile app uses. Sidebar links with no screen behind them yet render a placeholder instead of a blank page. Deployed env vars: `VITE_API_BASE_URL` only. Live URL: `https://admin-web-seven-vert.vercel.app`. The panel also renews its own session now: a 15-minute access token is exchanged for a fresh one through `POST /auth/refresh` instead of dumping the admin back to the login screen.

- EAS builds no longer depend on the machine that last ran Gradle locally. `android/build/generated/autolinking/autolinking.json` caches **absolute** paths, so a Windows-generated copy reaching the Linux builder made Gradle configure `:react-native-worklets` under `/home/expo/workingdir/build/android/C:/Users/.../node_modules/react-native-worklets/android` and fail with "Configuring project ... without an existing directory is not allowed". The nested `android/.gitignore` rules were not applied to the EAS archive, so a root `.easignore` now excludes `android/build/`, `android/.gradle/`, `android/app/build/`, `android/app/.cxx/` and the other machine-specific outputs. Delete those directories before a local build if the tree was ever built on another OS.

See `DEPLOYMENT.md`.
- The `EXPO_PUBLIC_API_URL` fallback in `src/services/client.ts` now points at the live backend instead of the Android emulator loopback (`10.0.2.2`), so a build with the variable unset can no longer ship a dead URL to a real device.
- Rider app: vehicle management and map-based base location. Riders can now switch vehicle type and update their registration number from **My vehicle**, and set their base pin from a searchable map (**Base location**). Vehicle changes are admin-approved — the proposal is parked on the profile as `pendingVehicle` and the live vehicle fields (used by dispatch and the admin map) only change on approval, with registration numbers checked for uniqueness across riders. - Supabase Auth OTP emails now show the 6-digit code (`{{ .Token }}`) instead of a "Confirm your email address" link. The default "Confirm signup" / "Magic Link" templates sent a single-use link whose token was already consumed or superseded (and with no allowed redirect it fell back to the default `http://localhost:3000` Site URL — the `otp_expired` screen). Added `npm run auth:config` (`backend/src/scripts/supabase-auth-config.ts`) to apply code-only templates, the production Site URL, allowed redirects (`swatcity://**`, Expo web dev), 6-digit codes and a 600-second expiry in one call; set `AUTH_EMAIL_REDIRECT_URL` only if a template keeps a link. Configure delivery in the Supabase dashboard (Authentication → Emails → SMTP); Gmail SMTP (`smtp.gmail.com:587` + Google App Password) is the documented setup because the built-in Supabase sender does not reliably reach Gmail. The optional "password changed" notice now uses generic `SMTP_*` env vars (formerly `BREVO_*`) and can point at any provider.
- OTP resilience fixes: a failed email send no longer burns a rate-limit slot (previously repeated failures locked the account for 15 minutes with a misleading "too many codes" error), a successful code verification now clears the request window so a legitimate user is never locked out by their own earlier attempts, and resending reports a failed send instead of pretending the code is on its way.
